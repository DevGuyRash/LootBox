# Pour Into: clean-stock and LuaBuddy acceptance plan

This is a runbook, not a gameplay result. Use the same built LootBox archive in both lanes and retain its SHA-256, file manifest, and the exact Project Zomboid build. Run `python3 tools/verify.py` first; passing Lua boundary fixtures does not replace these checks. Use disposable caches, worlds, displays, and ordinary non-admin accounts. Follow [the native launch and cleanup procedures](verification.md#actual-game-checks); don't edit an existing game, save, or user profile.

## Lanes

1. **Clean stock.** Start the stock client with only the tested LootBox archive installed. Capture a vanilla water-transfer menu first, then enable LootBox through stock Mods. Keep a single-player run and an ordinary stock multiplayer run with the matching archive enabled on the server; leave Lua checksum enforcement on. Confirm the server has no LuaBuddy runtime and no LootBox server script.
2. **Paired default LuaBuddy.** Use a clean client with the released LuaBuddy runtime at defaults and the same LootBox bytes through normal discovery. A fresh LuaBuddy install selects nothing: use its normal **Enable late** control for the discovered LootBox and **Load new profiles** in a live connection. Do not hand-create or change a profile, set an asset-mount flag, patch compatibility, or supply a server-side helper. Connect to a stock server with Lua checksum enforcement enabled and exercise stock profile restoration after join; capture loader evidence and a fresh context menu without restarting the client. Run the shelf-to-main and opt-in shelf-to-shelf cases again. Reconnect once and repeat after the default late mount. If this lane cannot use the normal default route, mark it blocked rather than substituting a helper profile.

For multiplayer, keep the fixture in a reachable real shelf/crate in the normal loot pane; use stock server-created items and non-admin clients. A second ordinary client provides an independent view of the shelf and can make competing moves. Do not add a Lua fixture to the tested package or turn off checksum, safehouse, or transfer validation to pass a case.

| Authority and conflicting work | Deny normal shelf access or make the destination ineligible. No retarget, duplication, unintended transfer, or dropped foreign action. If an admitted pour is partial, observed source loss equals target gain; record final holder, and do not mark restoration successful if blocked. Normal denied actions and checksums remain enforced. |

For each run, save the build/archive identity, effective checksum setting and join/late-mount log excerpt, named fixture/step, and before/after screenshots of source and target in their native inventory panes. Record item IDs, holder identity, liquid and amount before/after (in litres) from a read-only fixture observation independent of the submenu; for MP, include the second client or server-side observation with timestamps and any delayed or denied native transaction. A screenshot can prove menu or final placement, not the immutable ID or the server's receipt. Mark unsupported or unobserved cases separately; do not infer acceptance from the menu, animation, client-only completion, or absence of errors.
