# Native creation receipts (Build 42.22.2)

Opening a package or taking a mounted jug is not the same as transferring an existing item. Transfers know the original item ID. A stock producer can create a new ID. One reusable `LootBox/CreatedItemReceipt` boundary checks the exact owning action, exact receiving inventory, a bounded baseline of inventory IDs, and a producer-specific success condition. It never opens, moves, or consumes anything itself. Intake still computes the live hunger/thirst benefit from the result and uses vanilla Eat/Drink.

## Adapter contract

- `Receipt.begin(action, {inventory, matches, anchor, clock, ...})` captures the direct receiving container before the stock action changes it. `inventory()` must continue reporting that exact container. `matches(item)` must describe **all** possible outputs, not filter unsafe or ineligible lookalikes out of a comparison. `anchor()` returns true for the verified input/fixture transition, false or nil while pending, or a second error value on contradiction.
- Use `receipt:complete(action, {item=exactNativeResult})` only for the owned synchronous producer's exact reference; use `{id=authoritativeProducedId}` only if a stock receipt actually reports that ID for this action. Explicit identity can wait briefly for representation or source-state synchronization. A prior or foreign action cannot complete the receipt.
- `{ordered=true}` requires `deliveredBeforeDone(action, inventory)` to verify the stronger producer contract: a successful transition guarantees one matching item is already visible and retained in this exact inventory at the actual completion barrier. For example, a verified stock synchronous local producer can prove this in one call. Novel existing items, missing items, and ambiguous multiple additions cannot be substituted. This mode freezes the completion-time reference; it never adopts a post-Done lookalike. `preserveMatching=true` additionally requires previous members of the output class to retain exact object identity; `maxMatches` may lower that class's bound.
- `receipt:poll()` returns nil while pending, true plus its one confirmed result, or false plus a reason. `receipt:cancel(reason)` is terminal. The owning action must keep its normal cancellation, source-access, safety, movement, and queue guards. The producer's true completion barrier must be established by its specific adapter; generic queue drainage is not such a barrier.

The single-player canned routes use the stock handcraft's own exact created reference and consumed input list. Kept/unsealed drinks in multiplayer use their original ID, not a creation inference. **There is no new multiplayer fresh-ID completion claim in this change.**

## What ordinary multiplayer exposes

The stock zero-bite canned recipe creates its result on the server, then independently adds to main inventory or drops at the server character's current square. It destroys the selected input separately. The result's ordinary add packet carries the container and items, not the recipe/action/input ID; the action's stock Done carries no item ID. A positive stock Open and Eat sends a result ID but also immediately orders a fixed portion. That is not an opening-only receipt. `ReplaceInventoryItemInContainerPacket` would carry old and new identities for an actual direct replacement; the mapped peach recipe and jug Take do not use it.

The installed game normally sends relevant adds/removals and Done in reliable order. In an ideal trace where the mandatory output is successfully received before Done and remains in the watched inventory, an unrelated earlier lookalike either was already in the baseline or makes the delta ambiguous. A later lookalike cannot replace the frozen result. This conditional path is exercised in the domain suite. It is **not** a general delivery contract:

- NetTimedAction's server Accept stops earlier generic timed actions, but stock finite Lua actions do not expose that per-action acceptance fence. Local start/progress is not a server acceptance. The ordinary Lua completion/force-complete observation cannot identify the newly created item.
- Even a positive Done does not guarantee a visible product. The stock handcraft returns true from complete even if the native recipe didn't produce a result. When it did, a ground drop can be at an unobserved/delayed square, or disappear before a later sample. The current locally loaded square is useful as an exclusion, not authoritative receipt.
- The player's main inventory is the jug's mandatory destination on a successful stock Take, but a send can catch an exception and continue, and receiver application is guarded by current cell and container availability. A fixture transition or reliable transport ordering does not acknowledge successful item application. There is no stock Lua per-item receiving event with the creating action's ID.
- These permit two identical observable snapshots: exact selected shell gone (or jug stand changed), genuine Done, and one fresh matching ID in main. In one history that ID belongs to the operation; in the other it is a delayed lookalike and the real result is absent. The regression requires both unattributed histories to refuse selection.

Referenced installed entry points: `ISHandcraftAction.performRecipe/complete`, `Actions.addOrDropItem`, `ISAddTakeDispenserBottle.complete`, `RecipeCodeOnCreate.openAndEat`, `AddInventoryItemToContainerPacket`, `AddItemToMapPacket`, `INetworkPacket.send`, `NetTimedActionPacket`, `LuaTimedActionNew.update`, `ActionManager.setStateFromPacket`, and `ReplaceInventoryItemInContainerPacket`. No wire hooks or timing/portion sentinels are used. Live ordinary multiplayer is still unverified.
