# LootBox design

LootBox is a provisional name. This is an independent Build 42 client mod, with executable code exclusively in `media/lua/client`. A multiplayer host may enable the mod through the normal mod list, but installs no LootBox server logic. Native game actions remain authoritative. It has no dependency on LuaBuddy or any of the four reference mods.

## One language for the player

A category is a reusable selection of items. Native categories come from the current game's item catalog, including installed mods; no fixed category mapping compresses or drops them. A custom category contains item types, native categories, and other custom categories. Includes mean union. Cycles are refused. Stable IDs are independent of translated names.

Container labels describe what belongs there and accept multiple categories. Item labels add a particular instance to categories; adding an item type to a custom category affects every instance instead. Keep protects an instance from automated movement and deletion. Loot checklists describe what the player wants to find and require no tagging of world containers or individual loot. These are different player intentions with separate controls.

## One job model

Every operation is a source scope, an item selection, and a destination. Loot brings matching items to carried storage. Move sends them to a selected container, a floor location, the remembered vehicle, or labeled storage. Clean hauls them to real trash cans and batches native deletion. The same selection supports an item type, multiple native or custom categories, or all unprotected items. Source scopes include inventory, within reach, current room, current building, and a rectangle on one floor; including carried contents and recursing into bags are explicit options.

Ordinary scopes take a finite source snapshot. Building jobs capture the native room list and lazily divide each rectangle into sections of at most 8 by 8 tiles on its actual floor. The cursor yields during metadata enumeration, scans one section at a time, and retains no full tile or section list. It never calls `BuildingDef.getSquares()`. Loaded sections can be inspected without forcing the character onto an obstructed room center; native container approaches still govern transfers. Unloaded sections use normal coordinate or loaded-frontier walking and a finite streaming wait. A current-floor frontier can lead toward distant stairs before the desired floor loads. Permission, path, geometry, and streaming failures remain unsearched rather than becoming empty rooms.

Jobs revalidate each native action against live state. Source anchors retain location and fixture, bag, or keyed-vehicle identity so a capacity-limited delivery can return after source chunks unload. Floor coordinates resolve to the current native square, and immutable item IDs and types prevent substituting another item or source. The runner does not read unloaded inventories, assume another player's inventory remains unchanged, or wait forever for future loot respawns. Cancel stops owned work and restores temporary vehicle access where native actions permit restoration.

## Routing and capacity

Explicit destinations win. Labeled storage considers every matching label, then stable destination order, while reserving shared capacity across the planned batch. The runner rechecks actual capacity before transfer. Vehicle storage prefers the trunk, then native seat/other storage; access uses native doors, seats, keys and unlock actions. A full destination does not silently become a floor drop. Floor placement is an explicit destination.

Carried admission has two independent constraints. Native `hasRoomFor` and effective capacity govern each container; the main inventory's live `getCapacityWeight()` and `getEffectiveCapacity(player)` govern weighted mass across all carried destinations. Only the outermost directly carried bag applies equipped or fake-equipped reduction to nested contents. Attached unequipped bags use their native hotbar ratio. Shared preview reservations count positive mass changes across all bags, and runtime recomputes each pickup. A nonpositive rearrangement remains allowed while already overloaded. Carried bag destinations are independent of source traversal. Feasible bags precede main inventory and prefer the lowest actual marginal mass, preserving stable order on ties. The normal HUD threshold is informational; native hard admission remains authoritative.

Trash discovery identifies static bins across nearby loaded building floors and ground level without treating identity discovery as contents approval. Remembered bins retain native identity and last observed capacity; unloaded locations differ from bins observed to be gone. Current safehouse permission filters discovery, routing, and approval without erasing denied locations. Bin selection models the carried batch and known remaining weights, carrying trips, travel, incompatible items, whole-bin emptying operations, and travel and deletion still owed to other touched bins. Deferred travel uses a conservative return trip for each pending bin rather than claiming a globally optimal final tour. Initial travel uses an explicit estimate; completed owned walks populate a bounded directional cost cache. No separate path behavior or custom terrain pathfinder competes with the player's native path. Failed routes are excluded for the current job, and all capacities and identities are checked again on arrival.

A newly found or unloaded bin is physically approached and inspected. The runner then enters `needs_review`, retaining its cursor, records, carried items, and private request. A fresh transient review token captures client-observed contents. Approval rechecks reach, identity, protection, and membership before resuming the same job; rejecting the bin tries another, and cancellation invalidates the token. An observation wait, explored flag, or item-handle change is not a server acknowledgment. Native empty-trash deletes the entire server bin and ignores client approval IDs, so client checks cannot make shared-bin deletion atomic. The UI states this limit. Multiplayer `TrashDeleteAll` must permit the action. Cleanup does not change respawn settings or guarantee respawn; the server owns that policy.

Inspection knowledge retains the live parent and square, not a boolean attached only to a metadata key. Identity resolution retires it when a bin unloads or disappears. A live replacement on the same square cannot inherit inspection or an active target's approval. Bin review tokens must be issued and non-nil before approval or rejection. Successful approach observations are recorded at the action boundary, including floor walks. A walk gets 60 seconds without progress and a ten-minute total ceiling; transfer, trash, and vehicle deadlines remain independent.

## Interface

One LootBox context-menu entry contains only relevant shortcuts for an item, category, actual clicked container, floor location, or vehicle. Settings can hide the entry or individual groups. Quick shortcuts run directly by default through the same fresh planner and native runner. Transfer previews, cleanup previews, arrival bin reviews and quick-progress display have independent saved preferences. Visible reviews persist their checkbox choice only after a successful start or approval. Manual Preview remains explicit. Protected contents and native rules remain authoritative even with every review disabled.

Per-container shortcuts capture the exact native container at the click boundary. Inventory-page sidebar hooks preserve the previous callback and read the pooled button's current inventory on every click. Bag buttons use the existing item-menu event, with a separate contents context for the inner inventory. The native no-item pane menu binds the currently displayed pane. Blank space in a populated pane follows the game's selected-item menu; use its container icon for contents workflows. World objects expose each compartment separately. All paths use one contents-menu builder and the ordinary review/composer; none changes item, capacity, permission, or trash behavior. Unpacking into main inventory is an explicit container destination, because carried-storage looting deliberately skips already-carried items.

Context entries require an action icon role in the shared add/submenu factories. A local role table owns verified native texture keys. Different roles use distinct symbols; repeated source scopes or targets for the same action reuse their role. Bag-content headers can use the native item renderer, retaining the actual game or mod bag icon. No texture is copied into the mod.

Home offers common tasks, saved setups, last-setup continuation, and the first-run guide. Actions retains the full "Move [what] from [where] to [destination]" composer. Category lists distinguish custom and game content without removing native categories. Labels separates storage rules from item-copy tags and Keep. Help contains complete workflows, prerequisites, expected results, troubleshooting, and setup links. Native Options entry buttons expose the manager, categories, Help, and Settings without reloading other mods' preferences.

Named setups capture portable request fields rather than native object handles or approvals. Container targets bind to fresh context, vehicles use the remembered car, and area coordinates remain world-scoped. Optional setups and global interface preferences have their own checked Store documents, separate from categories, labels, and Keep. Their failure does not disable ordinary transfers. An explicit contextual action takes priority over remembered broad selections.

The visual layer uses measured native fonts, slate panels, amber actions, cyan custom content, sage results, and coral deletion/error cues. Labels and markers accompany color. The local row renderer constrains complete glyph rectangles and backgrounds to the viewport even when a partial row would otherwise be submitted. Native combo popups remain independent. Native control colors are copied per instance, and only owned text entries are unfocused when their page is removed or hidden.

## Runtime module contract

`Categories` owns category IDs, graph validation and matching. `Store` owns local versioned persistence. `Catalog` reads installed native script items. `Survey` owns the finite native room-section cursor. `Routing` owns the pure bin cost model and bounded observed travel cache. `Carry` owns contents-aware native bag and slot planning. `Recovery` owns durable whole-personal-item staging intents and observed restoration. `World` owns loaded source and destination discovery, source anchors, and static bin identity. `Native` owns native action submission and owned-walk observation. `Jobs` owns finite planning, progressive walking, delivery, and transient bin approval. `Setups` validates portable requests and interface preferences. `App` owns per-local-player state and persistence APIs. `Widgets` owns themed controls, viewport bounds, and text-entry focus ownership. `Menus` builds context requests; `Guides` supplies workflow records; `UI` owns manager, review, progress, and area-picker windows. Every execution path calls the same App preview/start API.

`App.catalog()` returns `{items={{fullType,name,categoryId}}, categories={{id,name,kind}}}`. Native category IDs are `native:<raw display category>` and missing categories use the item's native type category. Custom categories use `custom:<stable ID>`. Custom definitions are `{id,name,types={fullType,...},includes={categoryId,...}}`. `App.saveCategory(definition)` returns `id` or `nil,error`; `App.deleteCategory(id)` refuses deletion while referenced.

`App.get(playerIndex)` returns a per-player application. `app:preview(request)` returns a plan with `moves`, `skipped`, `warnings` and `request`; each display row has `itemName`, `from`, `to` and an optional `reason`. `app:start(plan,options)` starts the reviewed plan with optional per-job `{reviewBins=false}`. `app:pause()`, `app:resume()` and `app:cancel()` manage owned work. `app:status()` returns state, done, moved, cleared, deferred, total, reason and control availability. Requests have `{scope,area,sourceContainer,includeInventory,includeBags,filter,destination}`. Filter is `{ids={categoryId,...},types={fullType,...},all=boolean}`. Destination is `{kind,ref,labels}` with kind `inventory`, `floor`, `container`, `vehicle`, `labels`, or `trash`. Area is `{x1,y1,x2,y2,z}`.

`app:labels(container)` returns category IDs; `app:setLabels(container,ids)` persists them. `app:itemLabels(item)` and `app:setItemLabels(item,ids)` manage instance memberships; `app:protect(item,value)` changes Keep. `app:rememberVehicle(vehicle)` sets the hauling vehicle. `app:knownVehicles()` returns observed vehicles. `app:currentContainer()` returns the selected native loot container. Persistence is local; sharing labels between players is outside the client-only contract.

`app:reviewBin()` returns a transient review while the job waits in `needs_review`. `app:approveBin(review,options)` and `app:rejectBin(review)` accept only that current token. Public display mutations do not extend its private item approval. Category edits remain blocked while a job waits for review. Status includes `survey` counters and unsearched-room details, plus a routing explanation that distinguishes estimated and observed travel.

## Acceptance

Independent expected behavior comes from the original user request and installed native game sources. Build the whole runtime before adding tests. Verify player workflows first in an isolated game cache and display, then integration and category/persistence contracts where gameplay does not cover boundaries. Multiplayer requires a disposable normal server with client mod activation and no LootBox server files. No test may modify the user's running game, personal saves or Workshop sources. Portable and native-interpreter tests alone cannot establish working multiplayer gameplay.

## Cooperative input and stopped checkpoints

Native reports temporary admission contention as `busy` and a settled incidental interruption as `yielded`. Jobs waits for arbitrary queued player work without a list of food or action classes. Aiming and attacking/shoving pause until explicit Resume. Deliberate run/sprint input stops with a resumable checkpoint; Escape is not a blanket veto because it also closes UI. Death and sleep stop active work. Queue cleanup removes only owned work and preserves foreign action references and ordering. Completion by immutable item ID and type takes precedence over classifying an interrupted action, including a short observation grace for a stopped multiplayer transfer.

Jobs retains an operation and its completion continuation because dispatch may already have advanced a source, walking, or cleanup cursor. Cancel settles owned native work and retains a private stopped checkpoint. Resume restores that same execution and applies any already observed completed mutation once. It re-resolves anchored endpoints and returns to original floor locations before new work. Container continuations consume current resolved endpoints rather than handles captured before a long pause. Temporary vehicle restoration context outlives a yielded native action so cancelling during another player action still restores the original seat or outside state afterward.

Resume retires bin review tokens and deletion approvals. Every subsequent bin transfer and deletion must pass fresh inspection, including an operation created by an already completed callback. A sent deletion stays under native observation; it is never blindly replayed. Stopped checkpoints are transient to the current player session and are replaced by a new job or discarded on disconnect/main-menu reset.

All framed windows resize through native grips and update existing controls in place. Layout does not rebuild pages, persist drafts, replace controls, clear focus, or reset scrolling during a drag. Minimum heights account for native font row height and leave room for the resize grip. Shared list rows retain full plain text and separate item, decision/status, and description segments; item/status columns reserve space so long names cannot hide the decision.

Settings owns one unsaved preference-selection map and persistent list rows. Its introduction and Save/message controls remain outside the scrolling viewport. Descriptions wrap through native font measurement, and native per-row heights drive scrolling and hit testing. The shared renderer checks each complete glyph against the viewport, including visible description lines after a title scrolls away, so correctness does not depend on native child-panel stenciling. Only Save persists preferences.

## Exact stack selection

Select amount is a top-level conditional item action. SelectionRequest captures the native pane and inventory, group name, player, original member references, and displayed maximum. Confirmation refreshes and resolves that same group; a reused floor inventory cannot adopt unrelated same-name items. It validates a positive decimal integer against the current count and never reduces the amount silently. No item transfer, job, or inventory mutation is submitted.

Partial selections expand real native rows and use truthy child-only markers. Native saveSelection writes an item marker for the representative; the owned restore adapter normalizes that marker for expanded multi-item groups so a refresh cannot select the header and make a later drag take the whole group. Full counts preserve the native collapsed group marker. One unselected sentinel child remains rendered after a partial amount to prevent native header completion from counting an unrelated following row.

The native 50-row limit is a shared class field. Four instance wrappers scope it to the owning pane during selectIndex, onMouseDown, restoreSelection, and renderdetails. Weak pane state retains the largest requested partial render limit. An external base and nested call depth isolate another pane's default or own limit and restore the prior class value on success or error. Every known inventory/loot pane is attached through the existing refresh event, including default-limit panes. Nothing persists a global limit.

The numeric prompt owns its entry, button callbacks, validation, and color picker. It releases only its focused entry before removal and removes the separately registered picker. Cancel never applies a selection. Disconnect and main-menu cleanup close owned prompts. The workflow is mouse-only because native controller updates replace mouse selection.

## Personal hauling and deletion outcomes

An exact work registry joins source identity, native item ID and full type. A dispatched native trash snapshot settles registered source work only after those exact identities disappear. Successful in-place cleanup increments cleared, while successful delivery increments moved; done is their sum. Deletion also remembers identities observed before later source registration. Capacity failures defer finitely and retry only after successful unloading or gear changes advance the capacity revision. Sent trash commands remain observed through cancellation until their snapshot disappears or the native timeout expires.

Carry planning uses the actual remaining selected work and all observed bag candidates within the reviewed source scope. Native worn-location and clothing-extra metadata owns compatibility. Occupied equipment is retained. Native conversion observes the replacement ID and exact direct contents, then migrates private labels and work references. Capacity-only preparation failures may retry once at a changed capacity revision.

Recovery writes a separate verified Store receipt before staging and before each native intent. It reserves an ordinary static container and exact personal root/descendant identities. Operations bypass ordinary selection protection only when they match that durable intent. Preparation excludes the selected heavy source ancestry and preflights both heavy admission and raw bag readmission in a feasible restore order. Recovery streams and approaches the recorded endpoint before movement, then observes each transfer and original-slot restoration. Failure retains the receipt, and a failed manual recovery retains the original paused checkpoint while requiring recovery before ordinary Resume.

Review display uses App identity and monotonic review generation, separate from short-lived approval tokens. Automatic polling uses existing sessions only; manual Current job access can initialize the in-world session to expose a persisted recovery receipt.

## Matching transfers and optional reviews

Inventory routing remains the Smart Load policy. An explicit carried container instead transfers directly into that container without a temporary inventory leg or unrelated bag preparation. The matching destination has portable mode displayed or nearby and requires inventory sources with nested bags. At preview, World captures native matching-type aliases and container anchors from the current visible loot targets. Private target snapshots stay out of the public preview request and saved setup documents. Native sorting orders the detached source list once, and Jobs retains one ordered carried batch across bags. Floor routes capture their original drop point.

Matching registers two native inventory-control handlers immediately after their corresponding stock handlers. It uses stock textures with a native-font ALL badge and native control layout. Hover previews cache briefly, while clicks always recompute. Missing native control capability disables only the companions. The matchingTransferButtons preference is independent of context-menu visibility.

Review preferences default off and preserve explicit saved values. App.reviewPreference owns the mapping from transfer, cleanup or bin review to its preference and uses review when stored preferences cannot be read. App.start applies the default bin policy unless a per-job option overrides it. Failed preference writes do not undo an already started job and produce a notice. Successful direct quick actions stay quiet unless showQuickProgress is enabled or a meaningful notice needs display.
