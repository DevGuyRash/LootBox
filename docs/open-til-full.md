# Open and use the live Til Full amount (42.22.2)

This is a client-only convenience over ordinary inventory amount and handcraft actions, not a new recipe or a network command. Only the selected stack and its original reachable source/main inventory are eligible. A successful opening by itself never counts as food or drink consumed.

- **Mapped replacement in single player:** the stock handcraft's own created-item data must supply exactly one suitable consumable output and list the selected shell as consumed. The deterministic callback-only routes below also observe the synchronous stock perform with the same strict inventory checks; their results are not in the mapped output list.
- **Kept item in multiplayer:** a native keep + IsSealed + Unseal input and a unique network ID/full type allow a follow-up after the main-inventory copy is actually unsealed. Native pickup can reconstruct that copy under the same ID. Stock OpenCanOfBeverage specifies DontPutBack; if the unsealed survivor is instead observed in an external holder, choose Til Full on that item yourself. No second pickup or sip is attempted in that case. Inventory collisions, expired updates and cancellation do not trigger consumption.
- **Mapped replacement in ordinary multiplayer:** stock `OpenCannedFood`, `OpenCannedFood2` and `OpenJarOfFood` can continue only when the local result is isolated. Permit exact native pickup (if needed), keep any required opener in main inventory, confirm receiving space, and establish a quiet before-start snapshot. The same action's completion must show exact shell retirement and precisely one new direct main-inventory result of the native mapper's script/type. A jar must additionally create exactly one new `Base.JarLid` with the selected jar's saved lid condition (the stock default is 9). Both new IDs must be present at completion and retain exact refs/holders throughout settlement. An unrelated carried change, floor result, foreign action, missing companion, or late substitute is refused. A plain mapped Open has no server-supplied result ID, so this is strict local correlation, not packet-level lineage.
- **Callback-only stock opening:** `OpenWaterRationCan` creates one `Base.WaterRationCanEmpty` filled with 0.300 L of pure water. Observe that exact fluid owner, type, amount, capacity and purity; neither the obsolete dummy item nor a preexisting water can counts. `OpenUnlabeledCan` and `OpenDentedUnlabeledCan` select one stock result from the game's explicit canned-food set. In MP, a temporary read-only listener requires that the existing `recipe` opened-item notice name the same fresh ID before the owned action completes, in either receive order. The notice lacks the local player slot, so this route is unavailable in split-screen. It does not change or replace the game's handler. An unsafe dented result is never consumed.
- All eligible follow-ups size a portion from the opened item's live condition and current need, never the shell. The final stock Eat or Drink request checks that exact item (and, for water, its fluid component). Duplicates, tainted/liquid changes and unsafe food fail closed.
- Starting the first action in an empty native queue can happen inside the call that adds it. The mapped-opening receipt and the exact main-inventory bite/sip guard are attached before the action is added, including when vanilla mask removal precedes the bite and rewear follows it.
- **Canned drinks:** vanilla opened canned fruit beverage and canned milk are Food items with the native Drink command. The native food action/quantity units apply; the actual thirst change of the opened item determines the requested portion. Fluid cans still use the native fluid action. The existing optional both-needs preference is unchanged.
- A fallback sibling is added only for the enabled native OnNewCraft row of a supported producer. The normal amount submenu wins when both exist. Sharp-tool substitutions (which can cause an injury), alcohol, and bulk unpacking such as candy, buns and egg cartons are not opened and automatically consumed by these routes. If you open one manually, use the existing native actions for the actual result.

## Stock evidence

- `media/scripts/generated/recipes/recipes_cannedFood.txt`: OpenCannedFood consumes the can and maps Base.CannedPeaches to Base.CannedPeachesOpen. OpenCannedFood2 is also a mapper; the opening callback is RecipeCodeOnCreate.openAndEat.
- `media/scripts/generated/items/food.txt`: closed CannedMilk has OpeningRecipe but not CantEat; CannedFruitBeverage lacks OpeningRecipe. Both opened Food items have CustomContextMenu = Drink. Their exact live values may differ from defaults.
- `media/scripts/generated/recipes/recipes_fluids.txt`: OpenCanOfBeverage keeps its selected item and unseals it; no new item is a receipt. Alcohol stays excluded.
- `media/scripts/generated/recipes/recipes_jarring.txt` and installed `RecipeCodeOnCreate.applyLidCondition`: stock first sends the mapped food, then the Java callback creates the condition-matched lid; stock retires the shell last.
- Installed `RecipeCodeOnCreate.openWaterCan`, `openMysteryCan` and `openDentedCan`: each creates one direct main-inventory result as an OnCreate side effect before stock retires the shell. The ration is filled before the add. The two random cans stamp `NoLabel` and send their stock cosmetic output-ID notice, with no native fixed bite. Food's normal item serialization carries poison state as well.
- `media/lua/client/ISUI/ISInventoryPaneContextMenu.lua`: the regular amount and plain-recipe callbacks are independent. OnNewCraft builds native handcraft/transfer/return actions from clicked inputs. The stock tool, source and action requirements remain in charge.
- `media/lua/shared/Entity/TimedActions/ISHandcraftAction.lua`: local perform executes the recipe only when not an MP client. On the server complete executes it, and the normal add/drop routine sends only the destination and new item. Stock records how many inputs of a given type an output used, not their individual IDs.
- `media/lua/shared/ActionManager.lua`: Open adds/checks carry capacity and sends the result before the recipe destroys/synchronizes the selected input. Observe inventory room before stock submits the craft and matching floor changes before its completion. Both local observations must be present at native perform; a later standalone arrival is never accepted.
- The native crafting UI's `getOutputMapper():getOutputItem(data, true)` API reports the item script for the selected manual inputs. LootBox resolves and checks this script for supported recipes instead of guessing the opened item's name.
- Installed `zombie.scripting.logic.RecipeCodeOnCreate.openAndEat` returns for a nonpositive eat percentage (or a full moodle). A positive percentage sends only onlineID, output itemId, and the fixed fraction. `media/lua/client/ServerCommands.lua` immediately enqueues that exact fixed bite if the item is already present. This is not an opening-only receipt; there is no transaction/input ID in the command. LootBox never requests a dummy serving, hooks that handler, or issues a server command.

## Reproduce without starting the game

```sh
python3 tools/verify.py --game "$PZ_GAME_DIR" --evidence /path/to/new-evidence-directory
lua5.1 tests/stock/open-til-full.lua "$PZ_GAME_DIR"
javap -c -p -classpath "$PZ_GAME_DIR/projectzomboid.jar" zombie.scripting.logic.RecipeCodeOnCreate
```

The optional stock smoke executes the installed stock Lua against mocked Java/transport edges. The mapped MP integration test drives the production controller and adapter over simulated native action and item boundaries. Neither this nor the verifier's installed-Kahlua run proves live multiplayer behavior.
